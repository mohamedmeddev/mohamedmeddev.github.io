Autonomous content pipeline

99 nodes · 4 sources

Problem

Daily publishing from four sources. Roughly 60% of incoming items were duplicates, and editorial work consumed several hours every morning before anything shipped.

Approach

Every article is converted to a semantic embedding, then compared by vector distance rather than keywords — duplicates are dropped before a single token is spent on drafting. Unique items go through LLM drafting, image generation, and publishing, with every step persisted to Postgres.

Result

Zero human steps in the normal path. When something breaks, the run is routed to a separate error workflow that asks an LLM to explain the failure in plain language before alerting.

Multi-source URL security scanner

76 nodes · 3 threat APIs

Problem

Users submit suspicious links. Checking them by hand is slow, and a single API is not enough — while every check consumes a limited daily quota.

Approach

Shortened URLs are resolved first, then scanned in parallel against VirusTotal and Google Safe Browsing. VirusTotal analyses are submitted and polled across five cycles until complete. Results are cached so repeated links never re-spend quota, usage is rate-limited per user, and every input is parameterised before touching the database.

Result

Response time went from minutes of manual checking to seconds. Quota is preserved, and every scan leaves a full audit row in Postgres.

Resilient media retrieval service

66 nodes · failover

Problem

Users requested media links that frequently failed — upstream services go down, files exceed limits, and one user can exhaust the shared allowance for everyone.

Approach

A primary extraction API with an automatic fallback, file-size validation before download, a cache layer to avoid repeat work, per-user rate gating, separate audio and video paths, and a quality fallback when the requested format is unavailable.

Result

Failures return a clear message instead of silence. One heavy user no longer degrades the service for others, and every request is logged for usage reporting.

Arabic document localization pipeline

multi-agent · RTL

Problem

Translating structured documents into Arabic destroys the layout — tables, numbering, and heading hierarchy all break, and fixing them by hand costs hours per file.

Approach

A multi-agent pipeline: one agent extracts document structure, one translates with a controlled termbase, one reviews, and one rebuilds the layout for correct RTL rendering — including tables and typography. Output is reviewed by a native Arabic speaker.

Why it matters

Arabic quality is the one thing a monolingual team cannot verify internally. This pipeline produces a formatted Arabic document from a foreign-language source, with human review limited to checking, not rebuilding.

The difference

Most workflows tell you they failed. Mine tell you why.

A generic error handler sends you a stack trace at 2am and you spend the next hour guessing. Every system I build routes failures to a dedicated handler that feeds the context to an LLM and produces a readable diagnosis — what broke, where, and what the likely cause is.
